### Payload models

There is one per §3.1 type: `PriceReported`, `AnomalyDetected`, `BandUpdated`, `PriceChecked`, `DailyTick`.

### RedisStreamsBus

- **Publish:** `XADD spm:events MAXLEN ~ 100000 * type <t> body <json>` in a pipeline.
- **Consume:**
  1. `XGROUP CREATE … $ MKSTREAM`, ignoring `BUSYGROUP`.
  2. Loop on `XREADGROUP … COUNT 10 BLOCK 5000 >`. The block is abandoned as soon as `stop` is set.
  3. Events of other types are ACKed and skipped. The rest are ACKed after the handler succeeds.
- **Reclaim:** every 30 s, and once at startup, it runs `XAUTOCLAIM` on entries idle for more than 60 s and reads
  each one's delivery count with `XPENDING`.
  - A failure on the 5th delivery sends the entry to `XADD spm:events:dlq` with
    `type, body, group, entry_id, deliveries, error`, then ACKs it.
  - An entry already delivered more than 5 times (a crash loop) goes straight to the DLQ.

### EventBridgePublisher

`PutEvents` in batches of at most 10, with `Source="spm"`, `DetailType=<type>`, `Detail=<envelope json>` and
`EventBusName`. boto3 runs in a thread. Any failed entry raises `PublishError`.

### Outbox services

- **`OutboxPublisher.flush(events)`:** called after commit. It publishes, then marks the rows published. Failures are
  logged and swallowed, and it returns False.
- **`OutboxSweeper.sweep()`:** republishes rows unpublished for more than 30 s, in batches of 100. It holds the rows
  locked while publishing; on failure it bumps their attempts and stops.

### Worker runtime

- **`run_consumers`:** SIGINT and SIGTERM trigger a graceful stop. Each spec runs in a `TaskGroup`. With a database it
  sweeps the outbox once on start.
- **`idempotent(consumer, handler, *, uow_factory, clock)`:** turns `handler(event, uow)` into a `Handler`. Inside the
  handler's transaction it checks `seen`, then claims the event with `mark`, runs the handler, and commits.
- **`log_event`:** the debug consumer.

## Deviations (also in the Decision log)

- **`core/events.py` imports pydantic and orjson,** which the plan specifies but which conflicts with §2.3.
- **`Event.data` is JSON-ready,** with Decimals as exact strings.
- **`flush` takes events and returns a bool.**
- **The DLQ follows exactly 5 failed handler runs,** with crash-loop protection.
- **`idempotent` marks first, then runs the handler,** inside one transaction.
- **New `ProcessedEventRepo` port;** the container has separate `bus` and `consumer` fields.
- **The debug-log consumer is on by default locally.**

## Known limitations

- **No business consumers are registered yet.** Scoring arrives in M13, alerts in M16, metrics in M18.
- **The sweeper only runs once, at worker start.** The every-minute schedule comes in M17.
- **The memory unit of work is only partly transactional:** processed marks are, the other memory repos aren't.
- **`spm:events` is capped at about 100 000 entries.** A consumer group that falls further behind than that loses the
  trimmed entries. They are ACKed when reclaimed, not dead-lettered.
