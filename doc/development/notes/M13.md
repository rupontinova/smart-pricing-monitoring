# M13 — Scoring worker

**Status:** ✅ done 2026-10-22, on branch `develop`. The write → score loop now works end to end.

## What was built

### `services/scoring_service.py` (`ScoringService`)

`handle(event, uow) -> ScoringOutcome` runs inside the consumer's transaction:

1. **Lock and state check.** Take `advisory_lock("score:{product}:{area}")`, *then* check the state. If the report
   isn't `queued` (a replay, or unknown), skip.
2. **Load.** The product and area come from the catalog cache; the reporter's α/β give high trust; the new report's
   observation (with trust) comes from `report_assessments`.
3. **Context.** One area query over `max(30 d + 48 h, market window, corroboration window)` is sliced into shop
   history, market, same-shop recent and shift evidence. `stats.area_median` (SQL `percentile_cont`) gives the 90-day
   median.
4. **Classify** with `classify(ctx)`, then `assessments.save` (state `scored`).
5. **Pending resolution.** `resolve_pending` runs over the shop's PENDING reports, then `assessments.resolve` and the
   trust deltas are applied. If the new report is PENDING and confirmed a pending outlier, it becomes SHOP_OUTLIER too.
6. **Reputation.**
   - NORMAL or MARKET_SHIFT: `settle_normal` against unsettled same-shop peers.
   - BAD_REPORT by relative bounds: +0.5 β.
   - Then `add_evidence` and `mark_trust_settled`.
7. **Anomalies.** SHOP_OUTLIER (new or promoted) or MARKET_SHIFT go through `open_if_absent` with the key
   `kind:area:product:shop|*:direction`. A newly opened anomaly emits `anomaly.detected`. For MARKET_SHIFT it also
   sets `set_rebase(now − 48 h)`.
8. **Band.** `BandService.recompute` runs, then `band.updated` (skipped while the band is still empty).
9. **Daily rollups.** Today's `price_stats_daily` rows are upserted for the area and for this shop, using the report's
   area-local day.
10. **Outbox.** The events are added to the outbox.

Bad data (`ValueError`, such as an unknown product) rolls back, marks the assessment `failed` with the reason, and
returns normally. Transient errors propagate, so the bus retries.

`after_commit(outcome)` runs once the commit succeeded:
- `OutboxPublisher.flush`
- `BandService.publish_to_cache` (newer-wins)
- metrics: `reports_scored{classification}`, `scoring_ms`
- one `report_scored` log line with the timing

### Repositories

- **`PgAssessmentRepo`:** the full `AssessmentRepo`, including the new `get_observation`, `unsettled_for_shop`,
  `resolve` and `mark_failed`.
- **`PgAnomalyRepo`:** `open_if_absent` (`ON CONFLICT (dedup_key) WHERE status = 'open' DO NOTHING RETURNING`) and
  `recent`.
- **`PgStatsRepo`:** `upsert_daily` (never overwrites a `final` row), `series`, `area_median`.
- **`core/rollup.py`:** `local_day`, `day_bounds`, `compute_daily_stat`, which M17 reuses.

### Hot cache

`put_snapshot(band, prices, ttl)`: band and shop prices in one Lua script, refused if the cached band's `computed_ts`
is newer. It's in Redis, in memory and on the `HotCache` port.

### Worker and entrypoints

- **`workers/runtime.py` (`idempotent`):** a handler may return an after-commit callback.
- **`workers/scoring.py`:** `scoring_consumer(container)`, which is `idempotent("scoring", …)` for `price.reported`.
  `consumer_specs(container)` is used by `spm worker` and Lambda.
- **`spm worker`:** registers scoring, plus the debug log consumer locally. It exits with a message (code 1) when
  there's no DB or Redis.
- **`entrypoints/lambda_sqs.py`:**
  - parses the EventBridge envelope from each SQS record and dispatches by `detail-type`;
  - failures are returned as `batchItemFailures`;
  - it keeps one event loop for the life of the Lambda container, because pooled connections are bound to it.

### Event bus

- The bus has its own Redis client: socket timeout = block + 10 s.
- The consumer retries transient Redis errors with backoff (0.5 s, doubling to at most 10 s).

## Bugs found while building this

1. **A market shift could never be detected in real scoring** (an M11 design gap). A shock's first reports are
   PENDING, and the shift evidence ignored PENDING, so no shop ever looked shifted. The M11 fixtures had labelled
   shocked reports NORMAL, which hid it. The recent window now counts PENDING.
2. **`ON CONFLICT` failed from the 6th upsert on a connection.** The `'*'` in `COALESCE(shop_id, '*')` was a bind
   parameter. Postgres switches prepared statements to a generic plan at the 6th execution, after which the index
   inference fails. It's now a literal.
3. **The worker died on an idle stream.** `XREADGROUP BLOCK 5000` against a client with a 5 s socket timeout. Only
   running `make dev` showed it.
4. **Test speed.** The `NullPool` test fixture paid about 100 ms per connection, so e2e took 252 s. With a pool it
   takes 26 s. `NullPool` had also hidden bug 2.

## Known limitations

- **PENDING reports that start a market shift stay PENDING.** They aren't relabelled MARKET_SHIFT when the shift is
  detected, so they don't count toward the new band; they expire in M17. The band still moves, through the
  MARKET_SHIFT reports that follow.
- **Old dev data never gets scored.** Reports submitted before the scoring consumer existed (e.g. the M08 benchmark
  runs on the dev DB) stay `queued`, because the `scoring` group was created at `$`, so only events published after
  that are read. A one-off re-publish (or M17's maintenance) would score them.
- **The concurrency test calls the handler 20 times via `asyncio.gather`** rather than 20 Redis consumers. The
  contention is the same (separate transactions on the same advisory lock).
- **Shop prices from one device and network stay unverified.** Reports from the same IP within 10 minutes aren't
  independent, so localhost-only manual testing never shows `verified=true`. That's correct behaviour.
