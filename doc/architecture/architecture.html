Smart Pricing Monitor — system architecture

Crowdsourced grocery prices that answer one question in under a second: “Is the price I’m being quoted right now fair?” The system separates three causes of an unusual price (a bad report, an overpriced shop, or a market-wide shift) before alerting anyone. Orange badges A–G mark what sets it apart from a typical price tracker; they’re explained below the diagram.

What makes it different

AA fair-price verdict, not just a price list

The main screen takes the price you were just quoted and returns fair / high / suspicious, the verified fair range, how fresh the data is, and the cheapest verified shop nearby with the saving.

Typical tracker: shows a table of past prices and leaves the judgement to you.

BUnit-normalized prices

“500 g for 40”, “1 kg for 75”, “a tray of 30 eggs” are converted to one base unit (per kg, per dozen) before comparison, and local names map to one product.

Typical tracker: compares raw numbers, so a pack-size difference looks like a price jump.

CGuardrails at the door

A report must come from within about 300 m of the shop, is de-duplicated and rate-limited, and is checked against per-item sanity bounds. Likely unit mistakes (×2, ×12) get a “did you mean…?” hint.

Typical tracker: accepts every input and cleans it up later, if at all.

DTrust-weighted consensus

Each reporter has a reputation that rises when later reports confirm theirs and falls when reports contradict them. A price is shown as VERIFIED only after two independent reports, or one from a highly trusted reporter.

Typical tracker: one user, one vote, and the last report wins.

EA 3-way anomaly classifier

An unusual price has one of three causes: the report is wrong, the shop is overcharging, or the whole market has moved (an onion price shock, for example). The system tells them apart, so users get alerts only for the last two and real market moves don’t flag every shop.

Typical tracker: a single threshold that flags the market shift at every shop and lets bad data through.

FFreshness decay

Every report loses weight over time with a half-life set by how volatile the item is (onions change faster than rice). If there is no recent data, the app says “stale” instead of presenting an old number as current.

Typical tracker: a 3-week-old price looks exactly like today’s.

GEfficient by design

The write path does only cheap, constant-time work and emits an event. Scoring runs asynchronously and recomputes only the affected item × area. Reads are served from precomputed Redis bands, and with serverless parts the system costs close to nothing while idle.

Typical tracker: runs aggregate SQL on every page view, or a batch job over all data every night.

How the anomaly classifier decides

Check (on normalized price p)ResultAction
Outside hard bounds (< 0.2× or > 5× the 90-day area median)BAD_REPORTQuarantine it, suggest a unit fix, lower the reporter’s trust slightly
≥ 3 shops in the area moved the same way (|zshop| > 3) within 48 hMARKET_SHIFTRe-base the fair band and send one area-wide alert, not one per shop
|zmarket| > 3 against other shops, and corroborated (≥ 2 independent reports or 1 high-trust report)SHOP_OUTLIERAlert subscribers and suggest the cheaper verified shop
|z| > 3 from a single uncorroborated reportPENDINGDon’t alert yet: confirmation promotes it, contradiction turns it into BAD_REPORT
OtherwiseNORMALUpdate the band, the trend and the reporter’s trust

z = (p − median) / (1.4826 · MAD). Median and MAD are robust statistics, so a few bad reports can’t drag the baseline. This needs no ML infrastructure in the MVP; SageMaker or Isolation Forest is an upgrade for when there is enough data.

Two hot paths

Report a price (write)

PWA → API Gateway → POST /reports → Normalizer → Guardrails → INSERT (append-only) → emit price.reported → 202 Accepted. Then, asynchronously: SQS → Scoring worker → Trust + Classifier → update the Redis band → anomaly.detected → SNS.

Check a quote (read)

PWA → GET /check?item=onion&price=95&shop=s3 → Redis lookup for the band and cheapest-nearby set → verdict with confidence and freshness. Postgres is used only on a cache miss.
